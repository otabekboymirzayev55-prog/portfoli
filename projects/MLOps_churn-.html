04 / Machine learning delivery

Churn MLOps

A telecom churn application connecting a training pipeline, model tracking, a prediction API and a Streamlit dashboard.

scikit-learn / MLflow / FastAPI / Streamlit

Source code ↗

Local application · container tests passed

The problem

A model endpoint, dashboard and deployment setup have to agree on inputs, service addresses and model readiness. Each component can look complete while the combined application fails.

How it works

The project uses scikit-learn for modelling, MLflow for tracking, FastAPI for prediction and Streamlit for the interface. Docker Compose describes how the services run together.

Training & tracking → model artifact → FastAPI prediction → Streamlit dashboard

Engineering decisions

  1. Validate requests at the API boundary

    Prediction inputs are checked before inference, so invalid requests receive an explicit response.

  2. Separate readiness from process startup

    Readiness checks make model availability visible instead of assuming that a running API process can already predict.

  3. Check the service connection

    API_URL, dashboard requests and container service configuration were aligned. A Windows launcher supports the local workflow.

What was checked

19 local automated checks passed. API-to-dashboard HTTP connectivity was tested. GitHub CI also started the Docker Compose services and checked their integration.

Verification recorded October 30, 2026. Automated checks and live service checks cover different things.

Current limits

These checks establish application integration, not predictive performance or production capacity. No newly measured model-quality or latency figures are claimed here. The application has not been deployed to public hosting.

Next step

Document reproducible model evaluation and compare against a baseline, then measure the deployed service under representative load.
