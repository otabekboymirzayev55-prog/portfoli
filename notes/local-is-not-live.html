A local success is only one deployment check

An implementation note from the portfolio projects.

The missing boundary

A successful local chat establishes that one machine has a working combination of code, credentials, data and network access. It does not establish that the same combination exists on the public host. This distinction mattered when the Gemini-backed applications worked locally while the public API reported its provider as unconfigured.

Configuration belongs to an environment

A key in a local .env file does not appear in a hosting environment automatically. The server must receive its own secret configuration. Provider keys should stay off the frontend and out of Git. The public interface can load while its backend is unable to call the model.

An embedding index is part of the application

Changing embedding providers requires attention to the index, not just the API URL. The projects use separate collections or paths for the new embedding model, preserving the former index. The hosting environment needs the new index too, together with a retention or rebuild strategy when storage is ephemeral.

Health and usefulness answer different questions

A process health endpoint can establish that the API is running. A configuration flag can establish that a setting is present. Neither proves that the provider key is valid, quota is available, retrieval works or the browser can complete a request. A representative browser-to-API request supplies different evidence.

Report the boundary honestly

Useful status descriptions are specific: local document question answered; public provider configuration pending; container integration passed; public deployment not checked. Keeping those statements separate makes the next task clear and avoids presenting a partial deployment as a working public application.
